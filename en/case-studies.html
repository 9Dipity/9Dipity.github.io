    Retail · Full Package
    Fashion Boutique · Riga · Physical store + WooCommerce e-commerce

    Inventory sync and management portal for a Riga fashion boutique

    A women's clothing boutique with a physical store in Riga and a WooCommerce online shop was managing stock entirely in Excel. Staff updated the spreadsheet manually after each sale — but with two people doing this independently, the spreadsheet was constantly out of date. The result: orders for items that weren't in stock, angry customers, and hours every week spent reconciling discrepancies.

    They'd looked at off-the-shelf inventory solutions, but none handled their specific combination of in-store and online sales well, and the monthly SaaS fees added up to more than they wanted to spend.

    What we built

    We delivered a Full Package: a purpose-built SQL Server database, a web-based stock management portal, and integration with their existing WooCommerce store.

    • SQL Server database: products, variants (size, colour), stock levels, supplier records, sales history, customer records
    • Web-based management portal (runs in browser, works on tablets at the counter) for stock intake, stock counts, and manual adjustments
    • WooCommerce sync: stock levels update automatically when an online sale occurs; the portal reflects it within 60 seconds
    • Low-stock alerts: email notification when any variant drops below a configurable threshold
    • Supplier purchase orders: create POs in the portal, receive stock against them, automatic stock uplift on receipt
    • Daily sales report: emailed automatically each morning with top sellers, margin by category, and stock health
    • Their existing website left untouched — we connected to WooCommerce via its REST API

    Healthcare · Custom Software
    Dental Clinic · 3 Locations · Riga region

    Patient management system for a 3-location dental clinic

    A growing dental clinic had expanded to three locations over five years — but their administration hadn't kept up. Patient records were on paper at each clinic. Appointments were managed in a shared Outlook calendar that all three receptionists edited simultaneously (with predictable double-booking results). Billing was done in Excel, invoiced manually, and reconciled at month-end.

    They'd been quoted €40,000+ for enterprise dental management software. The quote also included features they'd never use and a per-seat monthly licence that would cost more each year as they hired. They needed something that fit their actual workflow — not a generic platform designed for dental chains with 50+ locations.

    What we built

    A web-based patient management system shared across all three locations in real time, with role-based access for reception staff, dentists, and management.

    • Central SQL Server database: patients, appointments, treatments, invoices, and staff across all three locations
    • Patient records module: medical history, contact details, treatment notes, photo attachments, GDPR-compliant data handling
    • Appointment scheduler: calendar view per dentist per location, conflict detection, SMS/email reminders to patients
    • Billing module: treatment-linked invoices, payment recording, outstanding balance tracking, monthly revenue reports
    • Staff portal with role-based access: receptionists see scheduling and billing; dentists see patient records; management sees everything
    • Runs in a browser — works on the existing computers at each clinic, no software installation
    • Data migration: historical patient records entered by staff during a 2-week transition period using an import tool we provided

    Distribution · Custom Software
    Import & Distribution Company · Baltic region

    Supplier pricing automation for a Baltic import company

    A company importing goods from 14 European suppliers was drowning in price lists. Every supplier sent updated prices differently — some in Excel, some as PDFs, some as CSV files, some embedded in emails. A staff member spent 3+ days every month downloading, reformatting, comparing, and manually entering prices into their sales system. Mistakes were common. Margin decisions were being made on data that was sometimes weeks old.

    What we built

    An automated supplier price management platform that ingests price lists in any format, normalises them, and serves up clean margin data to the sales team.

    • SQL Server database: suppliers, product catalogue, price history, exchange rates, margin rules
    • Price import engine (C#): handles Excel (.xlsx/.xls), CSV, and structured PDFs — each supplier's format configured once, then automated
    • Normalisation layer: maps each supplier's column names and units to a standard product catalogue (handles different SKUs, product names, packaging sizes)
    • Price comparison dashboard: shows current price vs. previous price, by supplier and product — highlights changes above a configurable threshold
    • Margin calculator: applies exchange rates, import costs, and margin targets to produce suggested retail prices
    • Alert system: emails the purchasing manager when a supplier changes prices by more than 5% on any product
    • Historical price charts: shows price trend per product per supplier over 24 months

    Banking · Regulatory Compliance
    Financial Institution · C#/.NET & SQL Server

    Building an automated SEC securities lending reporting system from scratch

    A major financial institution needed to comply with new FINRA securities lending reporting requirements. They had an existing SFTR system but nothing for SEC. The deadline was tight, the business logic was complex (20+ reporting scenarios), and there was zero room for error — T+1 deadlines with potential fines for non-compliance.

    What I built

    I designed and implemented the complete system over several months — database schema, C# processing engine, JSON file generation, SFTP transmission, and an 881-test automated test suite.

    • Normalised database schema with dedicated SEC tables, linked to existing SFTR data to avoid duplication
    • Event-driven C# processing engine handling 20+ distinct reporting scenarios
    • MD5 hash comparison for detecting actual data changes vs. redundant updates
    • Intelligent report type determination engine mapping SFTR actions to FINRA report types
    • BZip2-compressed JSON file generation with SFTP auto-transmission
    • Batch processing schedule aligned to trading hours (13:30, 16:30, 23:00)
    • 881 automated xUnit tests with parallel execution and CI/CD in Azure DevOps

    Banking · SQL Optimisation
    Financial Institution · Regulatory Reporting · SQL Server

    Reducing SFTR report generation from 15 minutes to under 2 minutes

    The main aggregation query was performing 47 table scans across tables with millions of rows. The stored procedure had grown organically over 4 years — every new regulation meant another subquery bolted on. Nobody had ever looked at the full picture.

    What I did

    • Replaced 12 correlated subqueries with indexed views for frequently accessed data combinations
    • Implemented incremental processing — only recalculating data that changed since the previous run
    • Refactored nested queries into well-indexed temporary tables with filtered indexes
    • Moved business logic calculations to persisted computed columns
    • Added carefully designed composite indexes aligned with actual query patterns
    • Implemented parallel processing for independent data segments

    The entire refactoring was done with zero production disruption. Extensive reconciliation testing verified that the new process produced identical results to the original.
